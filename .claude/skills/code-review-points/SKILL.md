# code-review-points: レビュー観点

**迎合禁止**: 「良さそうです」で終わらせない。各ペルソナで最低1つの指摘（または「なぜ指摘ゼロと言い切れるか」の根拠）を出す。

## 手順

1. 変更差分と、その変更が触れる呼び出し元・呼び出し先を読む（差分だけ見て済ませない）
2. 下の3ペルソナで順に検査する
3. AI生成コード特有パターン（下表）を機械的にチェックする
4. 指摘を重要度順（Critical / Should / Nit）で報告。**複数ペルソナが重複して挙げた指摘は重要度を1段上げる**

## 3ペルソナ

### 1. Saboteur（壊し屋）
「この変更を最小の入力で壊すには？」を考える。境界値・空・null・巨大入力・並行実行・部分失敗（途中でリトライ/クラッシュしたら？）・タイムゾーン/エンコーディング。

### 2. New Hire（新人）
「半年後に初見の人がこれを読んで正しく変更できるか？」。名前と実態の乖離、暗黙の前提、コメントすべき制約の欠落、一貫性のない設計パターン。

### 3. Security Auditor（監査人）
入力検証の欠落、認可チェックの位置（本当に全経路で通る？）、秘密情報のログ出力・ハードコード、インジェクション（SQL/コマンド/パストラバーサル）、IAM/CORS/公開範囲の過剰許可。

## AI生成コード特有の欠陥パターン（機械的チェック）

| パターン | チェック方法 |
|---|---|
| テストフィクスチャに本物らしい認証情報・実在メール | fixtures/テストデータをgrep（`AKIA`, `sk-`, `@gmail` 等） |
| クライアント公開変数にサーバー秘密（`NEXT_PUBLIC_*`, `PUBLIC_*`, `VITE_*`） | 環境変数のプレフィックスと中身の突合 |
| 認証・認可チェックの緩い比較（`==`による定数比較、大文字小文字無視） | 認証コードの比較演算子を確認 |
| 使われていない依存追加・importの置き土産 | 差分内の新規import/依存が実際に使われているか |
| エラーの握りつぶし（catchしてログだけ・空catch） | except/catch節の中身を確認 |
| 存在しないAPI・パッケージの幻覚 | 新規依存・新規APIは公式docs（context7/aws-knowledge）で実在確認 |

## スタック別の追加観点（本プロジェクト: React SPA + Hono/Lambda(TS) + DynamoDB + SAM）

- **Node/Lambda (Hono)**: ハンドラ肥大化、AWS SDKクライアントのリクエスト毎生成（モジュールスコープで再利用する）、Zod検証を通らない入力経路の混入、公開系(`/api/...`)とオーナー系(`/api/me/...`)の認可境界違反（design §4.2）、べき等性欠如（cleanupバッチ・退会段階削除は再実行安全が契約）
- **React/TS**: hooksの依存配列漏れ、浮いたPromise、レンダー内の副作用、リスト要素のkey欠如、IME composition中の入力確定（design §5.5）、地図インスタンスの再生成（`setData`差分更新が契約）
- **DynamoDB**: シングルテーブルのキー設計逸脱（design §6が正本）、GSIキーの設定漏れ/除去漏れ（公開切替時のGSI1、画像attach時のIMGSTATUS）、BatchWriteの未処理項目（UnprocessedItems）握りつぶし
- **IaC (SAM/CFn)**: `Resource: "*"` のIAM、削除ポリシー未指定のステートフルリソース（DynamoDB/S3）、ハードコードされたARN/リージョン、Cognito Liteティア指定漏れ
- **embed/セキュリティ固有**: CSP `frame-ancestors` 生成のドメイン検証漏れ（未登録・非公開時は `'none'`）、アップロード画像のmagic bytes検証スキップ、帰属表記の非表示化（常時表示が要件）
