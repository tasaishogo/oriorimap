| 選択肢        | 内容                                                                          | メリット                                                                          | デメリット                                                       |
| ------------- | ----------------------------------------------------------------------------- | --------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| **A（推奨）** | コア機能 + 重ね合わせ状態の保存・共有URL + 外部サイトembed。共同編集は第2段階 | ご指定のembedを含め「作る・探す・重ねる・埋め込む」の差別化価値を最短で検証できる | 共同編集を期待する協力者には初期は物足りない                     |
| B             | A + 共同編集も初期リリースに含める                                            | note記事の構想をフルで実現                                                        | 権限管理・競合処理の分だけ開発量が大きく増え、リリースが遅くなる |
| C             | 最小構成: 作成・公開・重ね合わせ表示のみ（重ね合わせの保存・embedは後回し）   | 最速でプロトタイプを出せる                                                        | 差別化要素（保存済みマージ地図・embed）が後ろ倒しになる          |

- デフォルト（未回答時）: A — 理由: ご指示のembed要望を初期から満たしつつ、開発量が跳ね上がる共同編集のみ後回しにするバランス
- あなたの回答: A(ただしCでも可)

## Q2. ログイン（アカウント）方式はどうしますか？ ｜カテゴリ: 外部連携・セキュリティ｜優先度: 高

認証基盤の選定・個人情報の取り扱い範囲に直結します。なお「公開地図の閲覧はログイン不要、地図の作成・編集はログイン必須」を前提としています（異議があれば回答欄へ）。

| 選択肢        | 内容                                                         | メリット                                                    | デメリット                                      |
| ------------- | ------------------------------------------------------------ | ----------------------------------------------------------- | ----------------------------------------------- |
| **A（推奨）** | Googleソーシャルログインのみ（将来LINE等を追加可能な設計に） | パスワードを預からないため漏洩リスク・実装/運用コストが最小 | Googleアカウント非保有者は作成側に回れない      |
| B             | メールアドレス+パスワード（ソーシャルログイン併用）          | 誰でも登録可能                                              | パスワードリセット等の実装・運用負荷が増える    |
| C             | LINEログイン中心（+Google）                                  | 日本の地域住民のカバレッジが最も広い                        | LINE Developersの申請・審査などの立ち上げの手間 |

- デフォルト（未回答時）: A — 理由: 趣味・小規模運用でパスワード管理責任を持たないのが安全かつ低コスト
- あなたの回答: B(幅広い利用者を受け入れたい)

## Q3. 共同編集はどの方式にしますか？（Q1でAやCを選んだ場合も、第2段階の設計・データモデルに影響します） ｜カテゴリ: ドメイン&データ・エッジケース｜優先度: 高

編集権限モデルとデータ競合処理の設計に直結します。

| 選択肢        | 内容                                                                            | メリット                                           | デメリット                                                                   |
| ------------- | ------------------------------------------------------------------------------- | -------------------------------------------------- | ---------------------------------------------------------------------------- |
| **A（推奨）** | 招待制の共同編集者（オーナーが招待。リアルタイム同期なし、後勝ち保存+更新履歴） | 実装コスト小で「複数人で地図を育てる」を実現できる | 同時編集がぶつかった場合は後から保存した内容が優先される（履歴から復元可能） |
| B             | 提案・承認型（第三者が変更を提案→オーナーが承認して反映）                       | 荒らし耐性が高く、オーナーが品質を統制できる       | 承認UI・差分表示が必要で開発量増。貢献の即時反映感がない                     |
| C             | リアルタイム共同編集（Google Docs風の同時編集）                                 | 編集体験は最良                                     | WebSocket/CRDT基盤が必要で開発・運用コスト大。小規模趣味運用には過剰         |
| D             | 共同編集は当面実装しない（オーナーのみ編集）                                    | 最小コスト                                         | note記事の構想（複数人での情報改善）が実現できない                           |

- デフォルト（未回答時）: A — 理由: 小規模運用では同時編集の衝突頻度が低く、招待制+履歴で実用上十分
- あなたの回答: A

初期コンテンツの立ち上げ（コールドスタート対策）に影響します。note記事では既存のGoogleマイマップ資産の活用に言及がありました。

| 選択肢        | 内容                                                                 | メリット                                                           | デメリット                                                |
| ------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------ | --------------------------------------------------------- |
| **A（推奨）** | GoogleマイマップのエクスポートファイルKML/KMZ + CSV の取り込みに対応 | 既存マイマップ資産（桐生かるたマップ等）を移行でき、立ち上げが速い | KMLの仕様差異（スタイル情報など）の吸収に一定の実装コスト |

- デフォルト（未回答時）: A — 理由: コールドスタート解消の効果が実装コストに見合う
- あなたの回答: A(ただしCでも可)

| 選択肢              | 内容                                                                  | メリット             | デメリット                  |
| ------------------- | --------------------------------------------------------------------- | -------------------- | --------------------------- |
| **A（デフォルト）** | 標準的で清潔なビジネスツール調（UIライブラリ標準テーマ）              | 追加工数ゼロ         | 没個性                      |
| B                   | メインカラーを1色指定し、それ以外は標準（例: 桐生の織物にちなんだ色） | 低コストでブランド感 | 色選定の判断が1つ増える     |
| C                   | 参考プロダクト・サイトを挙げてテイストを寄せる（回答欄にURL等を記入） | 完成イメージが揃う   | 参考先の選定が必要          |
| D                   | こだわりたい（印象キーワード・配色・密度を掘り下げる追加質問を実施）  | 理想に最も近づく     | ヒアリングがもう1往復増える |

- デフォルト（未回答時）: A — 理由: 地図コンテンツが主役でありUIの個性は後からでも足せる

- あなたの回答: D（織物、十二単を連想させるような派手すぎないが華やかさを感じさせるテイストがいい。認識合わせがしづらい気がするので、詳細設計のタイミングで3~5くらいデザイン案・モックを提示してもらってもいいかもしれない）
